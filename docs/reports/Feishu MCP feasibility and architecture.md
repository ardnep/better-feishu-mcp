# Build Feishu Access Around User Identity

> **Scope update after review:** Feishu Docs CRUD (create, read, update and delete) is now a core requirement, not a deferred extra. This report established representative reads only; mutation endpoints, user-token scopes, content fidelity, concurrency and deletion/trash semantics still require focused verification. See the current plan for the required Docs delivery track.

> **Decision update after review:** Build an independent TypeScript MCP using Feishu APIs directly. Do not reuse, fork, wrap or invoke existing Feishu MCP/CLI implementations. The comparison below is retained as research background; its recommendations to evaluate/reuse existing tools are superseded. The current implementation direction is in [the plan](../PLAN.md) and [the short HTML brief](../review/plan.html). Standard MCP, validation, testing and keychain libraries remain appropriate.

**A local, user-only Feishu MCP is documentarily feasible and worth evaluating, with reads as the independent first deliverable and sending as a separately gated option.** Creating an application and enabling bot capability is compatible with the requirement; adding its bot to group chats is not. Feishu documents user-token search, history, message retrieval, sending and replying, although generic bot-membership prerequisites conflict with the explicit user-token sections. The user's prior successful reads are relevant experience, not a test reproduced by this research. Personal OAuth consent does not remove app-scope activation, tenant policy, app availability or resource permissions, and neither approval-free access nor send availability can be guaranteed. Evaluate official tools before rebuilding: an improved open-source TypeScript server should differentiate through enforced user identity, minimal scopes, predictable read workflows and trustworthy write approval. This report and the accompanying plan authorize no implementation, credentials, app changes, live user-data calls, installation, remote deployment or publication.

Research synthesis dated **2026-11-04**, based on the three research notes indexed in the README. There was no earlier research to build on. Feishu China is the verified documentary scope; Lark global requires a separate audit. Primary-source documentation and repository claims are distinguished below from engineering recommendations and untested behavior.

## Explicit user routes justify reads without promising bot-free success

Feishu's message APIs explicitly accept `user_access_token`; these are not equivalent to tenant/bot-token routes. Group discovery returns groups joined by the identity represented by the token and excludes direct-message conversations. The user's own group membership, app scopes and message visibility remain relevant. **The project must never add the bot to a chat or fall back to tenant identity to make a failing user request work.** App registration, bot-capability enablement and chat membership are three different actions. ([Group listing](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/chat/list), [Permission model](https://open.feishu.cn/document/server-docs/application-scope/introduction?lang=zh-CN))

The following scope matrix is a documentary starting point, not a console-verified permission manifest. Paths are relative to `https://open.feishu.cn/open-apis`. Alternatives joined by OR are alternatives, not a request to grant all of them; AND is essential for history and sending. Request scopes under **user identity**, not similarly named application/event permissions.

| Capability | Endpoint | Exact user scope logic | Boundary and primary evidence |
|---|---|---|---|
| Joined group discovery | `GET /im/v1/chats` | `im:chat:read` OR `im:chat.group_info:readonly` OR `im:chat:readonly` OR `im:chat` | Prefer `im:chat:read`; app bot capability required, but token identifies user or bot; excludes p2p. [Reference](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/chat/list) |
| Group members, optional | `GET /im/v1/chats/:chat_id/members` | `im:chat.members:read` OR `im:chat` OR `im:chat:readonly` OR legacy `im:chat.group_info:readonly` | Calling user or bot must belong; same-tenant condition for internal groups. Returned list excludes bots, so it cannot prove bot absence. [Reference](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/chat-members/get) |
| Group history / message get | `GET /im/v1/messages`; `GET /im/v1/messages/:message_id` | (`im:message:readonly` OR `im:message`) AND `im:message.group_msg:get_as_user` | User token supported explicitly; generic bot-in-group prerequisite remains ambiguous. [History](https://open.feishu.cn/document/server-docs/im-v1/message/list), [Get](https://open.feishu.cn/document/server-docs/im-v1/message/get) |
| P2p history / message get | Same endpoints | (`im:message:readonly` OR `im:message`) AND `im:message.p2p_msg:get_as_user` | Separate chat-type scope, not covered by group permission. [History](https://open.feishu.cn/document/server-docs/im-v1/message/list) |
| Message search, preferred | `POST /im/v1/messages/search` | `search:message` | User token only; snippets/metadata, not guaranteed full bodies. [Reference](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/message/search) |
| Message search, older | `POST /search/v2/message` | `search:message` | User token only; IDs, with migration to IM search recommended. [Reference](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/search-v2/message/create) |
| Send / reply as self | `POST /im/v1/messages`; `POST /im/v1/messages/:message_id/reply` | `im:message` AND **`im:message.send_as_user`** | Dot before `send_as_user`; tenant availability and no-bot behavior require separate validation. [Send](https://open.feishu.cn/document/server-docs/im-v1/message/create), [Reply](https://open.feishu.cn/document/server-docs/im-v1/message/reply) |
| Add reaction | `POST /im/v1/messages/:message_id/reactions` | `im:message.reactions:write_only` OR `im:message` | User token supported; user or bot must be in conversation; separately approved write. [Reference](https://open.feishu.cn/document/server-docs/im-v1/message-reaction/create) |
| Recall | `DELETE /im/v1/messages/:message_id` | Reference lists OR `im:message`, `im:message:recall`, `im:message:send_as_bot`; exact user-eligible selection remains to verify | User token is listed, but scope identity, ownership/role and time-window rules need testing. Not deletion only from the user's view. [Reference](https://open.feishu.cn/document/server-docs/im-v1/message/delete) |

Search-only access is a useful smallest messaging milestone: `search:message` can supply snippets and chat/message identifiers without requesting body hydration. It is not an exhaustive DM directory or archive. History defaults to 20 messages, at most 50 per page; ordinary chat history returns thread roots, so replies require thread-container reads. Visibility restrictions include older-history settings, restricted chat types and invisible/deleted messages. The history error catalog also identifies apps with external sharing or associated organizations enabled as incompatible with user-history requests. Do not translate every failure into “admin approval required.” ([Search](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/message/search), [History](https://open.feishu.cn/document/server-docs/im-v1/message/list), [Get](https://open.feishu.cn/document/server-docs/im-v1/message/get))

**Generic bot-membership wording remains unresolved, not disproved.** History/get and send/reply references retain bot-in-group prerequisites while explicitly documenting user-token permissions. Feishu's official plugin guide separately advertises user-identity reads and writes, supporting the interpretation that a genuine user route exists, but not proving that every third-party app can use it without bot membership in the target tenant. The deciding experiment is a consenting user's existing ordinary group, with bot absence verified independently before and after each operation. Failure must preserve the no-bot constraint rather than trigger a membership workaround. ([History](https://open.feishu.cn/document/server-docs/im-v1/message/list), [Send](https://open.feishu.cn/document/server-docs/im-v1/message/create), [Official plugin guide](https://www.feishu.cn/content/article/7613711414611463386))

Sending is credible but optional: the official guide expressly warns that some enterprises, including ByteDance, do not support user-identity sending. There is no established universal process that guarantees newly obtaining `im:message.send_as_user`. Message editing documents only tenant-token support; message-file upload and resource download also document tenant tokens, with download including an app-in-chat restriction. Although the official plugin advertises user attachments, its exact public route or entitlement is unresolved. **User editing and no-bot attachment downloads must not be advertised as supported**, and cookies/private APIs are not an acceptable bridge. ([Official guide](https://www.feishu.cn/content/article/7613711414611463386), [Edit](https://open.feishu.cn/document/server-docs/im-v1/message/update), [Upload](https://open.feishu.cn/document/server-docs/im-v1/file/create), [Download](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/message-resource/get))

## Small scope bundles unlock breadth without erasing approval gates

Feishu's user-token surface extends far beyond chat. The representative endpoints below accept user tokens, but that does not make every API in their product family available to the user or review-free. Start with narrow read packs and preserve separate discovery, content, export and write capabilities. Prefer read-only alternatives over broad write scopes; a scope alone never proves resource access. ([Permission model](https://open.feishu.cn/document/server-docs/application-scope/introduction?lang=zh-CN))

|---|---|---|---|

Document editing, Base/Sheets writes, calendar scheduling, task changes, comments, imports/exports, file transfer, subscriptions, approvals, attendance/HR and meeting recordings belong in a broader discovery backlog, not a validated user-token feature promise. Each needs an endpoint-level audit of identity support, exact scopes, resource constraints and tenant availability before admission. The present evidence establishes representative read feasibility, not complete platform parity or a universal free-plan entitlement.

**Personal consent is one gate, not the whole authorization system.** Effective access combines app scope activation, actual user grants, app availability/installation, resource ACLs and tenant policy. Feishu explicitly permits developer user-token debugging without publication/review for eligible scopes, while excluding some sensitive scopes. This is a plausible explanation for the user's previous approval-free reads, not a diagnosis of their setup or proof of indefinite production exemption. Test enterprises offer a separate development route; their permissions do not automatically apply to production resources. ([Permissions and debugging](https://open.feishu.cn/document/server-docs/application-scope/introduction?lang=zh-CN), [User consent](https://open.feishu.cn/document/sso/web-application-end-user-consent/guide))

The minimal-friction order is to inspect an existing authorized app, investigate eligible developer debugging for the smallest next bundle, then use tenant-defined review-free scopes or normal custom-app release when necessary. Review-free scope activation and automatic approval can reflect prior administrator policy rather than absence of governance. Marketplace employee self-install is conditional on developer and tenant settings, activates only exempt permissions, and installs for the enterprise rather than only that employee. Publishing this project as a marketplace app introduces a separate ISV/review obligation; an open-source license grants no Feishu permission. **No approval guarantees can be made without the target console and policy.** ([Custom-app review](https://open.feishu.cn/document/best-practices/intro-to-custom-app-review), [Employee self-install](https://open.feishu.cn/document/uAjLw4CM/uYjL24iN/platform-overveiw/develop-process/configuring-employee-review-free-installation), [Marketplace publication](https://open.feishu.cn/document/isv-guides/publish-your-app/step7-publish-the-store-application?lang=zh-CN))

## Existing official tools change what a new server must improve

The official MIT-licensed `larksuite/lark-openapi-mcp` already supports OAuth, scope selection and explicit `user_access_token` mode; its README warns that `auto` can fall back to tenant tokens. Therefore “Feishu MCP cannot act as the user” is not a valid rationale for rebuilding. Its documented limitations include file upload/download and direct document editing, with non-preset API compatibility untested; its OAuth HTTP deployment documentation describes localhost-only use rather than safe shared hosting. Evaluate a pinned version with strict user mode and a tool allowlist before selecting a new implementation. ([Official MCP](https://github.com/larksuite/lark-openapi-mcp), [Configuration](https://github.com/larksuite/lark-openapi-mcp/blob/main/docs/usage/configuration/configuration.md), [License](https://github.com/larksuite/lark-openapi-mcp/blob/main/LICENSE))

The official MIT-licensed Go-based Lark CLI is another concrete baseline: it documents user/bot identity selection, OAuth, native keychain storage, history/search/send/reply, document/media workflows and schema inspection. A constrained TypeScript MCP facade could reuse it, but must pin its executable/version/output contract, use fixed argument arrays rather than a shell, and prevent bot identity and generic API escape hatches. Direct API adapters avoid subprocess/output dependencies; adapting the official MCP avoids rebuilding OAuth. These are alternatives to measure, not a predetermined rewrite. The official CLI's warning against adding assistant bots to groups aligns particularly well with this project's invariant. ([Official CLI](https://github.com/larksuite/cli))

Community `open-feishu-mcp-server` illustrates Workers-based remote hosting and the dual OAuth roles of MCP provider and Feishu client, but its documented `/sse` setup and broad authenticated-tool access are not the recommended transport/security baseline. AWS's AgentCore sample wraps the official CLI with per-user credential infrastructure but adds substantial hosting dependencies. These repositories provide implementation ideas, not independently audited security or comparative performance evidence. Pin commits and inspect code, licenses and notices before reuse; preserve upstream notices for derivative code. ([Community project](https://github.com/ztxtxwd/open-feishu-mcp-server/blob/main/README.en.md), [AWS sample](https://github.com/aws-samples/sample-lark-mcp-on-agentcore))

The proposed project's defensible improvement is **a small, auditable capability boundary**, not more generated endpoints: no identity fallback, clear permission diagnostics, bounded results with provenance, independent snippet/body/export packs, deterministic failure for unsupported user routes, and trusted preview/approval for writes. TypeScript fits an HTTP/schema-heavy npm-distributed server and shared local/hosted service layer; Go offers native packaging and reuse of the CLI, Python suits Python-owning teams, and Rust trades higher initial complexity for native control. This is engineering judgment, not a benchmark conclusion.

## Transport choice and confidential OAuth define separate trust boundaries

Start with a local TypeScript process over **stdio**, not a public service. Locality describes where a process runs; transport describes how MCP messages travel. Streamable HTTP can be local or hosted, while stdio is normally a client-launched subprocess. A local process still runs with the user's OS privileges and is not a sandbox; retrieved private content still reaches the configured MCP client/model. The currently served MCP specification describes newline-delimited stdio and HTTP POST messages with JSON or request-scoped SSE replies. Its 2026-07-28 model differs from older initialization/session-based examples; select clients and test compatibility rather than copying an old `/sse` tutorial. ([Transports](https://modelcontextprotocol.io/specification/latest/basic/transports), [HTTP binding](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http), [Security guidance](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices))

**The SDK v2 stable claim was independently rechecked during synthesis.** The retrieved upstream main README explicitly identifies split `@modelcontextprotocol/server` and `@modelcontextprotocol/client` packages as the stable v2 line implementing MCP 2026-07-28; npm's mutable `server/latest` record returned **2.4.0**, with Node `>=20`. These are source/registry observations on the research date, not an installation, provenance-signature verification or target-client compatibility test. Prefer the stable line indicated by verified sources, but pin the exact reviewed and tested release/runtime later; if source freshness or compatibility becomes uncertain, defer version selection rather than asserting stability from this report alone. Do not mix v1 examples with v2 imports or treat a minimum engine version as a supported-LTS policy. ([Upstream README](https://raw.githubusercontent.com/modelcontextprotocol/typescript-sdk/main/README.md), [Registry record](https://registry.npmjs.org/@modelcontextprotocol/server/latest))

Figma demonstrates why “MCP means a local npm process” is outdated. Its public remote offering uses `https://mcp.figma.com/mcp`, while the desktop app exposes local HTTP at `http://127.0.0.1:3845/mcp`; feature/entitlement and selection-context differences accompany these deployments. This is a delivery comparison, **not evidence that the Figma tools injected into this research environment are the same public product**, endpoint, auth flow or feature set. Feishu does not need to copy Figma's hosting model to support modern MCP. ([Figma remote setup](https://developers.figma.com/docs/figma-mcp-server/remote-server-installation/), [Figma desktop setup](https://developers.figma.com/docs/figma-mcp-server/local-server-installation/))

Upstream Feishu authorization is separate from MCP transport authorization. The current Feishu token reference specifies `https://accounts.feishu.cn/oauth/v3/token`, documents PKCE, and says Open Platform-created apps are **confidential clients requiring `client_secret`**. Public-client registration is not open; the documented exception is official Feishu MCP apps. PKCE does not turn an arbitrary third-party distributed app into a secretless public client. Older authorization guidance and v2 wording conflict, so test the v3 S256 exchange and refresh contract before release. ([OAuth v3](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/authentication-management/access-token/get-user-access-token-v3), [Authorization-code guide](https://open.feishu.cn/document/authentication-management/access-token/obtain-oauth-code?lang=zh-CN), [v2 migration notice](https://open.feishu.cn/document/authentication-management/access-token/get-user-access-token))

For local OSS distribution, recommend **bring-your-own app credentials**, stored locally in a keychain, never a shared secret shipped in source/npm/config examples. A centrally owned confidential app instead needs a trusted backend to hold its secret, changing the custody and operations model. Use an exactly registered loopback callback with state, S256, replay rejection and a short-lived listener; dynamic ports and `localhost`/`127.0.0.1` interchangeability remain unverified. Inspect actual returned scopes, request `offline_access` only when persistent login is wanted, honor returned expiry and serialize atomic refresh-token rotation because v3 documents single-use refresh tokens. Logout's local deletion and provider-side revocation are different operations. ([OAuth v3](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/authentication-management/access-token/get-user-access-token-v3), [Official localhost callback example](https://github.com/larksuite/lark-openapi-mcp))

If hosting is later justified, add a separate Streamable HTTP adapter with HTTPS, audience-bound MCP authorization, explicit client consent, per-user isolation, encrypted upstream credentials, resource metadata/discovery, origin validation and retention controls. A Feishu token must not double as an MCP bearer token; validating one does not authorize the other trust boundary. Current MCP guidance offers multiple client-registration strategies rather than requiring dynamic registration. Never broadcast the official MCP's localhost OAuth mode as a shortcut to safe multitenancy. ([MCP authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization), [Security guidance](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices), [Official deployment limits](https://github.com/larksuite/lark-openapi-mcp/blob/main/docs/usage/configuration/configuration.md))

## Exit gates turn documentary feasibility into a defensible release

The architecture should separate domain services, region-fixed Feishu adapters, OAuth/token custody, capability policy, curated tools and transport adapters. Effective access is the intersection of enabled tools, supported user identity, actual scopes, resource rights, local policy and operation approval. Check it at invocation as well as discovery. Default writes, sharing, deletion, exports and bulk indexing off; avoid generic HTTP/shell tools, arbitrary authenticated URLs and token-returning tools. Use bounded pagination/bytes/time, cancellation, provider-aware backoff and content-free redacted diagnostics. Treat messages/documents as untrusted data, never as instructions to change identity, acquire scopes or send information. ([MCP security guidance](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices), [CLI safety precedent](https://github.com/larksuite/cli))

The first live gate, only after separate authorization, records exact endpoint/token identity, actual scopes, app release/visibility, tenant context and results for search, joined-group discovery, no-bot group history/get, p2p history and thread replies. Verify bot absence using an independent trusted UI/admin view: the members endpoint excludes bots and cannot establish it. Sending receives a separate scope/tenant gate and a separately approved message to a named recipient; failed sending must not block read-only release. Unsupported editing/resources remain disabled. A successful controlled test establishes only that tested tenant/app/resource combination, not universal compatibility. ([Member listing](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/chat-members/get), [History](https://open.feishu.cn/document/server-docs/im-v1/message/list), [Send](https://open.feishu.cn/document/server-docs/im-v1/message/create))

A later implementation must test schema and scope logic, redaction, refresh races/crash recovery, callback state/PKCE failures, identity switching, hostile content, SSRF, cursor isolation, capped pagination and stdio cleanliness against selected clients. Writes need trusted approval bound to user, destination and payload, expiration and replay protection; a model-provided `confirm: true` is not human consent. Avoid retrying ambiguous sends without endpoint-supported deduplication or reconciliation. Before OSS publication, inspect the packed artifact, pin dependencies, retain third-party notices, scan secrets/dependencies, document supported Node/client versions and define incident/upgrade behavior. These are proposed acceptance criteria, not controls implemented by this research-only repository.

## Conclusion

The critical product boundary is not “bot versus no application”; it is **delegated user access without chat-bot membership**, enforced independently of API convenience. The most useful next evidence is a small, recorded no-bot read experiment under the user's actual app and tenant policy, compared with official tools—not a larger generated tool catalog or a premature hosted deployment.

A narrow read-only release can remain valuable even if user sending, attachments or approval-free production use prove unavailable. Treat those outcomes as capability limits with actionable diagnostics, not reasons to weaken identity, tenant governance or the user's no-bot constraint. The accompanying plan makes these limits explicit before any credentials or implementation exist.
