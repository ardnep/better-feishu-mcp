# Feishu user-token capability landscape and approval feasibility

Research date: 2026-11-04. Planning only; no credentials obtained, no application created, and no API calls against user data. Scope: Feishu China, using official `open.feishu.cn` documentation. User clarification: application/bot creation is acceptable; adding a bot to group chats is not. Messaging is researched separately.

## 1. Which broader capabilities can a local MCP expose as the user?

### Takeaway

Documents, Drive, Wiki, Base, Sheets, calendar, tasks, Minutes and even Feishu Mail have representative APIs explicitly accepting `user_access_token`. This is delegated API access, not an unrestricted reproduction of the Feishu UI: each operation still needs an enabled application permission of the correct identity type, user consent, and applicable resource rights. [Permission model](https://open.feishu.cn/document/server-docs/application-scope/introduction?lang=zh-CN); [User authorization](https://open.feishu.cn/document/sso/web-application-end-user-consent/guide)

### Cited Findings

Endpoint paths below are relative to `https://open.feishu.cn/open-apis`. “U + T” means the endpoint documentation accepts both user and tenant tokens; the recommended MCP route here is **U**, never an automatic fallback to T. Scope alternatives in one row are **OR**, not a request to enable every listed scope. These examples establish capability, not tenant-specific review-exemption status. [Scope interpretation and identity types](https://open.feishu.cn/document/server-docs/application-scope/introduction?lang=zh-CN)

| Category / useful MCP feature | Verified representative endpoint | Token / app types | Exact representative scope(s) | Resource and practical restrictions |
|---|---|---|---|---|
| Unified document/Wiki search | `POST /search/v2/doc_wiki/search` | U + T; custom + store | `search:docs:read` | Described as search of current user's visible cloud documents; `doc_filter` or `wiki_filter` required. Supports document types including DOCX, SHEET, BITABLE, FILE and Wiki; title/content-style filters and highlighted summaries. Page size ≤20, 100 requests/minute. Header table says U + T despite user-oriented description and user-token error text; use U and validate behavior rather than assert this endpoint is U-only. [Official API](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/search-v2/doc_wiki/search?lang=zh-CN) |
| Read document text | `GET /docx/v1/documents/:document_id/raw_content` | U + T; custom + store | `docx:document:readonly` OR `docx:document` | Calling identity needs document reading/editing rights. Error 1770032 explicitly distinguishes granting the user access via Share from granting a tenant-token app access via Add document app. 5 requests/second/application. Does not establish full fidelity for every embedded block. [Official API](https://open.feishu.cn/document/server-docs/docs/docs/docx-v1/document/raw_content?lang=zh-CN) |
| Browse Drive folders / discover object tokens | `GET /drive/v1/files` | U + T; custom + store | `space:document:retrieve` OR `drive:drive:readonly` OR `drive:drive` | Lists one folder level, not recursive. Missing folder token selects user's root; root listing has special no-pagination/no-shortcuts behavior. Not an exhaustive list of every document the user can open. [Official API](https://open.feishu.cn/document/server-docs/docs/drive-v1/folder/list?lang=zh-CN) |
| Resolve Wiki URL to underlying document/Base/Sheet | `GET /wiki/v2/spaces/get_node?token=...` | U + T; custom + store | `wiki:node:read` OR `wiki:wiki:readonly` OR `wiki:wiki` | Requires node view permission. Returns `obj_type` and `obj_token`; content must then be fetched through the matching document/Sheets/Base API. Wiki scope alone is not a content-read grant. [Official API](https://open.feishu.cn/document/ukTMukTMukTM/uUDN04SN0QjL1QDN/wiki-v2/space/get_node) |
| Base/Bitable record querying | `POST /bitable/v1/apps/:app_token/tables/:table_id/records/search` | U + T; custom + store | `base:record:retrieve` OR `bitable:app:readonly` OR `bitable:app` | Filter/sort/project fields; ≤500 records/page. **Advanced permissions can require management rights for this API**, otherwise success with empty data is possible. A user who sees a limited UI view must not be assumed able to retrieve the same data through this endpoint. Wiki-hosted Base first needs node resolution. Sensitive person fields have separate contact scopes. [Official API](https://open.feishu.cn/document/docs/bitable-v1/app-table-record/search?lang=zh-CN) |
| Read Sheets ranges | `GET /sheets/v2/spreadsheets/:spreadsheetToken/values/:range` | U + T; custom + store | `sheets:spreadsheet:readonly` OR `sheets:spreadsheet` (also broad Drive alternatives) | Identity needs spreadsheet read/edit permission. ≤10 MB response; cross-sheet reference and array-formula results not supported. Rendering options affect whether values or formulas are returned. [Official API](https://open.feishu.cn/document/server-docs/docs/sheets-v3/data-operation/reading-a-single-range) |
| Read calendar / synchronize events | `GET /calendar/v4/calendars/:calendar_id/events` | U + T; custom + store | `calendar:calendar.event:read` OR `calendar:calendar:readonly` OR `calendar:calendar` | Identity must be reader/writer/owner; primary/shared/resource calendars supported, Google/Exchange calendars excluded. Sync/page tokens supported, but time-window queries cannot paginate and may truncate. Error catalogue includes bot capability missing (190007): enabling bot capability may be necessary in some calendar flows; **this is not a requirement to join a group chat**. [Official API](https://open.feishu.cn/document/server-docs/calendar-v4/calendar-event/list) |
| Personal task list | `GET /task/v2/tasks` | **U only**; custom + store | `task:task:read` OR `task:task:write` | Only “我负责的” / tasks assigned to me (`my_tasks`), not every UI task view. Supports completion filter and pagination, ≤100/page. [Official API](https://open.feishu.cn/document/task-v2/task/list?lang=zh-CN) |
| Contact lookup / identity resolution | `GET /contact/v3/users/:user_id` | U + T; custom + store | For user-first route: `contact:contact.base:readonly`; names/avatar separately use `contact:user.base:readonly` | Email, phone, organization, employee ID etc. require separate field scopes. With U, organizational visibility policy determines accessible people; with T, application contact data range does. Department path additionally depends on admin profile-display settings. Prefer `open_id` to avoid requesting employee-ID scope unnecessarily. [Official API](https://open.feishu.cn/document/server-docs/contact-v3/user/get) |
| Minutes transcripts for meeting research | `GET /minutes/v1/minutes/:minute_token/transcript` | U + T; custom + store | `minutes:minutes.transcript:export` | Requires export permission on the actual Minute; read/view access alone is not established as sufficient. Optional speakers/timestamps and txt/srt output. Legacy `minutes:minute:download` no longer accepts new applications. [Official API](https://open.feishu.cn/document/minutes-v1/minute-transcript/get) |
| Feishu Mail message reading | `GET /mail/v1/user_mailboxes/:user_mailbox_id/messages/:message_id` | U + T; **custom only** | `mail:user_mailbox.message:readonly` plus field scopes `mail:user_mailbox.message.body:read`, `mail:user_mailbox.message.subject:read`, `mail:user_mailbox.message.address:read` as needed | U can use mailbox `me`; T requires mail-resource data permission. Requires an actual mailbox and message access; base read scope alone does not grant body/subject/address fields. Do not assume marketplace availability or low sensitivity merely because U is accepted. [Official API](https://open.feishu.cn/document/mail-v1/user_mailbox-message/get?lang=zh-CN) |

### Inferences

- Recommended first read-only modules: document text + Wiki resolution; then Drive/search; then Sheets/Base and personal tasks/calendar. Minutes and Mail are useful opt-ins, not default blanket scopes. This prioritization is a product/security recommendation based on the endpoint-specific restrictions above, **not** a verified universal list of review-free scopes.
- Keep discovery, metadata, content and export as distinct tool capabilities: search results do not prove permission to read the target, and read access does not prove export permission.
- None of the representative non-messaging endpoint prerequisites says to add the application's bot to a group chat. App registration, bot capability, resource sharing, and chat membership are separate concepts. Calendar's bot-related error is a reason to retain optional bot capability support, not to introduce group-join onboarding.

### Gaps

- Per-scope review-exemption labels cannot be certified for the user's tenant without its developer console/policy. The API docs show valid scopes/token types, not a guarantee that each is exempt or developer-debuggable.
- Create/edit/delete workflows (document blocks, Base schema/record writes, Sheets writes, calendar scheduling, task changes), comments, imports/exports, file downloads, subscriptions, approvals, attendance/HR, VC recordings and other platform categories need their own endpoint-level audit before inclusion. They are not declared unsupported; no unverified endpoint/scope is proposed here.
- The search API documentation has mixed identity signals; authenticated U testing is needed for exact result coverage, cross-tenant documents, content indexing and tenant availability.

## 2. Does user-scoped access avoid application publication or administrator approval?

### Takeaway

**Sometimes it avoids an individual approval step, but not by erasing the application authorization layer.** Official Feishu documentation explicitly allows many developer-user-token API debugging calls before app publication; it separately describes policy-defined review-free custom permissions and marketplace employee self-install. None establishes an unrestricted, permanently unapproved “personal production app” route. [Permissions, debugging and release](https://open.feishu.cn/document/server-docs/application-scope/introduction?lang=zh-CN); [Marketplace self-install](https://open.feishu.cn/document/uAjLw4CM/uYjL24iN/platform-overveiw/develop-process/configuring-employee-review-free-installation)

### Cited Findings

1. **Application API permissions remain app-scoped.** Feishu now explicitly distinguishes user-identity permissions from application-identity permissions, with different sensitivity/review requirements. A user token does not mean the app can omit applying for the user-identity scope. [Official permission model](https://open.feishu.cn/document/server-docs/application-scope/introduction?lang=zh-CN)
2. **Developer debugging exemption is real and relevant to the user's prior experience.** For supported permissions, after requesting them, the application's developer can use their own `user_access_token` to debug without publishing or waiting for review. The same page explicitly says some sensitive U permissions are not eligible; the console shows a notice. This is distinct from testing in a separate test tenant. [Official instructions, “方式一：使用 user_access_token 调试 API”](https://open.feishu.cn/document/server-docs/application-scope/introduction?lang=zh-CN)
3. **Test tenants are a different route.** Test-version permission changes can take effect without approval in the test enterprise. Those permissions do not automatically take effect in the formal application version; the formal version must reapply/release. This is not evidence of access to the employee's original organization's production resources. [Official instructions, test enterprise and formal release](https://open.feishu.cn/document/server-docs/application-scope/introduction?lang=zh-CN)
4. **Custom app review-free scopes can become effective immediately.** The tenant administrator configures which scopes are review-free. Scopes requiring review require a version and approval. Separately, administrators can configure automatic approval for a particular app or categories of custom apps. “No approval click now” can therefore reflect existing administrator policy. [Permission levels](https://open.feishu.cn/document/server-docs/application-scope/introduction?lang=zh-CN); [Review-free release rules](https://open.feishu.cn/document/best-practices/intro-to-custom-app-review)
5. **User consent is another gate.** Browser OAuth documentation requires app scopes to have been applied for and made effective, then requests the scopes from the user. Missing user authorization yields 99991679. Token exchange can fail for app not installed (20009), user outside app availability (20010), or app disabled (20069). [Consent guide](https://open.feishu.cn/document/sso/web-application-end-user-consent/guide); [Current token API](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/authentication-management/access-token/get-user-access-token-v3)
6. **Resource sharing and tenant policy survive OAuth.** Docx requires access to the particular document; Base advanced permissions may impose stronger API conditions; contacts U calls are limited by organizational visibility, and individual fields can depend on admin settings. Thus the general statement in the permission overview that U data scope follows the user is not an assertion that every UI operation or field is available through every API. [Docx](https://open.feishu.cn/document/server-docs/docs/docs/docx-v1/document/raw_content?lang=zh-CN); [Base](https://open.feishu.cn/document/docs/bitable-v1/app-table-record/search?lang=zh-CN); [Contacts](https://open.feishu.cn/document/server-docs/contact-v3/user/get)

| Gate | What it controls | What it does not replace |
|---|---|---|
| App identity and effective user-identity API scope | Whether this app may request/use an API ability | User consent or resource access. [Source](https://open.feishu.cn/document/server-docs/application-scope/introduction?lang=zh-CN) |
| User OAuth scopes actually granted | Which delegated abilities this token contains | App scope activation, app availability, resource permissions. [Source](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/authentication-management/access-token/get-user-access-token-v3) |
| Resource ACL / sharing / export / Base advanced role | Which specific resource/action the calling identity can access | API scopes. [Source](https://open.feishu.cn/document/server-docs/docs/docs/docx-v1/document/raw_content?lang=zh-CN); [Source](https://open.feishu.cn/document/minutes-v1/minute-transcript/get) |
| Tenant policies | Review exemptions, installation, app availability, organizational visibility | Consent to all future scopes. [Source](https://open.feishu.cn/document/best-practices/intro-to-custom-app-review); [Source](https://open.feishu.cn/document/server-docs/contact-v3/user/get) |
| Bot membership in a chat | A separate messaging concern | None of the preceding app/OAuth/document gates. The cited non-messaging APIs do not prescribe joining chats. [Representative document API](https://open.feishu.cn/document/server-docs/docs/docs/docx-v1/document/raw_content?lang=zh-CN) |

### Inferences

- Most plausible explanation for “I already read as myself without admin approval”: supported developer-token debugging, a scope already effective/review-free under tenant rules, or an already-authorized app. These are hypotheses consistent with official documentation, not a diagnosis of the user's prior setup.
- For a local personal prototype, developer-token debugging is a legitimate documented starting point to investigate—not something to dismiss as impossible. Do not market it as a guaranteed production authorization bypass.
- An approval-friction check should distinguish: cannot create app; scope pending; developer exemption unsupported; user grant missing; app unavailable; resource forbidden; tenant policy blocked. Reporting all as “needs admin” would hide actionable differences.

### Gaps

- No official guarantee found that developer debugging is a supported indefinite production deployment mode, nor a universal personal-only app flag allowing arbitrary employee production scopes without tenant policy/admin involvement.
- No access to the user's current app role, effective scopes, release state or tenant policies was used, so exact friction for their organization remains unverified.

## 3. Which setup/distribution path fits a local open-source TypeScript MCP?

### Takeaway

Recommend bring-your-own self-built Feishu app for local deployment, with user-token-first feature packs and narrowly requested scopes; investigate developer debugging first, then policy-exempt or normal release as appropriate. Marketplace distribution is a different ISV/product setup, not an automatic shortcut around tenant authorization. [Custom permissions workflow](https://open.feishu.cn/document/server-docs/application-scope/introduction?lang=zh-CN); [Marketplace release](https://open.feishu.cn/document/isv-guides/publish-your-app/step7-publish-the-store-application?lang=zh-CN)

### Cited Findings

| Path | Setup and approval dependencies | Practical conclusion |
|---|---|---|
| Self-built / enterprise custom app | Create/select app in developer console; configure redirect URL; request scopes specifically under user identity; for eligible developer U debugging, no publication required; otherwise scopes may take effect immediately under tenant exemptions or require version/review. Formal release includes app availability. [Permissions](https://open.feishu.cn/document/server-docs/application-scope/introduction?lang=zh-CN); [OAuth setup](https://open.feishu.cn/document/sso/web-application-end-user-consent/guide) | Best initial BYO-app route; no need to make group-chat bot membership part of document/calendar/task onboarding. |
| Existing published marketplace app | App must already be published and installed/enabled for tenant/user; standard permission model includes platform listing and tenant authorization. [Scopes](https://open.feishu.cn/document/server-docs/application-scope/introduction?lang=zh-CN) | Existing vendor approval may reduce new work, but credentials/token handling remain tied to that app. |
| Marketplace employee review-free installation | Developer enables “ordinary members can install without review”; employee install also requires tenant policy permitting it. Only review-exempt permissions activate; required-review permissions escalate to admin. FAQ explicitly says even employee installation installs the app **for the enterprise, not just themselves**. [Detailed official guide](https://open.feishu.cn/document/uAjLw4CM/uYjL24iN/platform-overveiw/develop-process/configuring-employee-review-free-installation) | Genuine conditional low-friction path, **not** personal-only installation or full-scope bypass. |
| Publish this MCP as a new marketplace app | Official release guide describes enterprise-oriented product, meaningful integration, SSO, privacy/security requirements, ISV qualification and staged review. Full/non-public listing is not the same as copying open-source code locally. [Release guide](https://open.feishu.cn/document/isv-guides/publish-your-app/step7-publish-the-store-application?lang=zh-CN) | Higher provider-side overhead; not the recommended first step for one local user. |
| Separate test enterprise/version | Test scopes operate in test enterprise; formal-version scopes/release remain separate. [Official workflow](https://open.feishu.cn/document/server-docs/application-scope/introduction?lang=zh-CN) | Useful for development fixtures; not proof of the target tenant's production authorization. |

- **Current OAuth implementation detail:** the fetched v2 token page is deprecated and points to `POST https://accounts.feishu.cn/oauth/v3/token`. Current v3 supports confidential/public clients, but explicitly says apps registered through Feishu Open Platform are **confidential**, require `client_secret`, and public-client registration is not open (only official Feishu MCP apps are public clients). Therefore a local open-source project must not assume secretless public-client PKCE registration is available. [Current v3 API](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/authentication-management/access-token/get-user-access-token-v3); [Deprecated v2 notice](https://open.feishu.cn/document/authentication-management/access-token/get-user-access-token)
- **Grant inspection and refresh:** v3 returns actual granted `scope`, which can be smaller than requested. `offline_access` is needed for refresh-token fields; refresh tokens are single-use; use returned expiration fields instead of fixed lifetimes. The official example uses a preconfigured localhost callback. [Current v3 API](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/authentication-management/access-token/get-user-access-token-v3)
- **Marketplace documentation inconsistency:** broad scope guidance says store permissions go through platform and tenant review, while the more specific employee-install guide documents review-exempt activation. Read the specific guide as a conditional exception, not evidence that the general authorization layer vanished. A development overview also labels employee-free installation as internal testing/contact-your-counterpart, while the detailed guide documents a switch; availability must be checked, not promised. [General scope guide](https://open.feishu.cn/document/server-docs/application-scope/introduction?lang=zh-CN); [Specific guide](https://open.feishu.cn/document/uAjLw4CM/uYjL24iN/platform-overveiw/develop-process/configuring-employee-review-free-installation); [Development overview](https://open.feishu.cn/document/isv-guides/publish-your-app/step5-develop-store-application?lang=zh-CN)

### Inferences

- Suggested architecture: per-tool manifest declaring endpoint, user-token requirement, alternative scopes, resource prerequisites and risk; feature-pack enablement from effective scopes; explicit opt-in writes/exports; no silent switch from user identity to tenant identity.
- Suggested rollout: (1) app + localhost OAuth + smallest Docx read pack; (2) confirm developer exemption eligibility and one explicitly shared/owned document; (3) add Wiki/search/Drive discovery independently; (4) add Sheets/Base/tasks/calendar as needed; (5) separately review Mail/Minutes and writes. Request only the next feature pack instead of an all-platform permission import.
- BYO-app local deployments should store each user's own app secret/token locally, never embed a shared vendor secret in distributable source. Coordinate refresh rotation to avoid consuming the same single-use refresh token concurrently. These are security/implementation recommendations derived from the confidential-client and token contracts, not code changes.
- Keep the provider profile explicitly Feishu China (`open.feishu.cn`, `accounts.feishu.cn`). Do not mechanically swap in Lark global domains or infer identical scope catalogs, exemption rules, marketplace eligibility or tenant behavior from English labels/occasional cross-product links in Feishu docs.

### Gaps

- Lark global was intentionally not independently verified; the findings must not be represented as a Lark feasibility audit.
- Marketplace self-install feature availability, trial limitations and exact per-scope exemptions need console/vendor confirmation. The release guide itself has inconsistent gray-release tenant counts; no limit is relied upon here.
- New v3 token semantics were fetched and verified, but a complete refresh/revocation/authorization-endpoint migration audit is outside this capability note. Do not copy older OAuth tutorial endpoints blindly.
- No SDK coverage, local project implementation, credentials, billing plans or actual production API success was inspected; this note establishes documented feasibility, not a working integration.
