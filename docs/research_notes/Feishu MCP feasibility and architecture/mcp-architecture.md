# Feishu MCP architecture and implementation feasibility

Research checked **2026-11-04**. Planning only; no installation, login, API calls, app changes, or secret handling performed. User clarification: creating an application/bot is acceptable; **adding the bot to group chats is not**. User-token reads are already known possible from the user's experience; sending as the user is desirable. Recommendations below are design judgments, not verified implementation behavior.

## 1. Which MCP delivery, SDK, and language should a new server use?

### Takeaway
Start with a local, user-only stdio server in TypeScript, keeping domain services independent of transport. Current official sources identify SDK v2 as **stable**, not prerelease; add hosted Streamable HTTP only after a demonstrated remote-client need and a separate authentication/isolation review. [SDK](https://github.com/modelcontextprotocol/typescript-sdk)

### Cited Findings
- MCP transports preserve the same protocol semantics. Standard choices are stdio (client-launched subprocess, newline-delimited JSON-RPC) and Streamable HTTP (independent HTTP endpoint, POST messages, JSON or request-scoped SSE responses). Therefore **local vs hosted is not the same distinction as stdio vs HTTP**. [Transport overview](https://modelcontextprotocol.io/specification/latest/basic/transports)
- Important date-sensitive change: the 2026-07-28 HTTP revision removes protocol-level sessions and the standalone GET stream. Earlier 2025 Streamable HTTP revisions had sessions and GET streams; SDK/client compatibility must be tested rather than copying an old tutorial. The separate 2024 HTTP+SSE transport is deprecated and should not be selected for a new implementation. [Current HTTP specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)
- The TypeScript SDK main README explicitly calls v2 (`@modelcontextprotocol/server`, `@modelcontextprotocol/client`) the stable line implementing MCP 2026-07-28. It dates the v2 release to 2026-07-27; v1 (`@modelcontextprotocol/sdk`) remains on `v1.x`, with fixes/security maintenance for at least six months after that release. This supersedes earlier guidance that main/v2 was prerelease. [SDK README](https://github.com/modelcontextprotocol/typescript-sdk)
- npm's `@modelcontextprotocol/server/latest` returned **2.4.0**, `engines.node >=20`, Apache-2.0, and an npm provenance attestation on this research date. Pin a reviewed release at implementation time rather than assuming this mutable dist-tag stays unchanged. [Registry record](https://registry.npmjs.org/@modelcontextprotocol/server/latest)
- The SDK supports Node.js, Bun, and Deno; v2 uses Standard Schema-compatible tool schemas and offers thin optional Node/Express/Fastify/Hono middleware. Its repository notes Apache-2.0 for new contributions with existing MIT code: inspect notices for copied code rather than assuming a single blanket license. [SDK README](https://github.com/modelcontextprotocol/typescript-sdk)
- Official Figma **remote** MCP uses `https://mcp.figma.com/mcp`, requires no desktop application, and signs the user into Figma. Current documentation recommends remote delivery and says only catalog-listed clients can connect, with a waitlist for new client developers. [Figma remote setup](https://developers.figma.com/docs/figma-mcp-server/remote-server-installation/)
- Official Figma **desktop** MCP is an application-hosted **local HTTP** service at `http://127.0.0.1:3845/mcp`, not stdio. Its setup explicitly selects Streamable HTTP in Codex, requires a Dev/Full seat on an eligible plan, and says desktop does not support canvas writing or sending UI to Figma. Desktop also supports selection-based context. [Figma desktop setup](https://developers.figma.com/docs/figma-mcp-server/local-server-installation/)
- These public Figma URLs verify the delivery example only. They do **not** establish that the tools injected into this research harness have the same endpoint, authentication, entitlement, or feature set. No inference about this session's Figma deployment was made. [Public remote documentation](https://developers.figma.com/docs/figma-mcp-server/remote-server-installation/)

### Inferences
- **Recommended local MVP:** TypeScript on a currently supported Node LTS; one installed CLI with `login`, `status`, `logout`, `doctor`, and `serve --stdio`. stdout must contain only protocol messages; diagnostics go to stderr. Local stdio avoids a permanently listening MCP port and minimizes hosting/token-custody operations; it still executes with local-user privileges and is not a sandbox. This preference follows MCP's local-security recommendation to use stdio to limit access to the launching client. [Security guidance](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices)
- **Hosted option:** independent Streamable HTTP adapter, HTTPS reverse proxy, user isolation, an OAuth authorization service, encrypted server-side credential store, and operational controls. Prefer simple request/response and SDK compatibility handling rather than custom protocol/session machinery. Local HTTP is an optional intermediate deployment, not a required phase. [HTTP specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)
- **Language tradeoff:** TS suits an API-bound tool server, typed schemas, npm distribution, and sharing adapters between local Node and hosted JS runtimes. Go is attractive for a single native executable, and the official Go-based Lark CLI makes wrapping/reusing Go work a concrete alternative. Python is reasonable for a Python-owning team but adds little to this primarily HTTP/schema workload; Rust buys tighter native packaging/control at greater initial implementation cost. These are engineering judgments, not benchmark claims. [TS runtime support](https://github.com/modelcontextprotocol/typescript-sdk); [official Go CLI](https://github.com/larksuite/cli)
- Use stable v2 for greenfield work, subject to target-client interop tests. Do not mix v1 imports/examples with split v2 packages. If a necessary client cannot interoperate, document a tested legacy compatibility strategy rather than choosing prerelease code or silently downgrading. [SDK and migration links](https://github.com/modelcontextprotocol/typescript-sdk)

### Gaps
- Target MCP clients and exact supported protocol revisions are not specified; compatibility is a release gate. No SDK, transport, or Node runtime was executed in this research.
- Figma account/tool entitlements and catalog availability may change; the comparison is not a promise of access or an endorsement of copying Figma's business model.

## 2. What already exists, and can user identity avoid group-bot membership?

### Takeaway
Do not reinvent generic Feishu API exposure: the official MIT-licensed MCP already supports user OAuth, explicit user-token mode, and messaging. First compare it and the newer official CLI against required workflows; a new project is justified mainly by enforced user-only identity, smaller reliable tools, secure credentials, and auditable write controls—not by claiming user tokens are unsupported. [Official MCP](https://github.com/larksuite/lark-openapi-mcp); [Official CLI](https://github.com/larksuite/cli)

### Cited Findings
- `larksuite/lark-openapi-mcp` identifies itself as the **official** Feishu/Lark OpenAPI MCP, package `@larksuiteoapi/lark-mcp`, currently described as Beta. Setup requires an app ID/secret, permissions, and a registered OAuth callback for user operations. Its README documents `login`, optional explicit scopes, `--oauth --token-mode user_access_token`, and says this mode covers personal documents and sending IM messages. It warns `auto` may fall back to tenant tokens. [Official README](https://github.com/larksuite/lark-openapi-mcp)
- Official configuration additionally supports an explicitly supplied `USER_ACCESS_TOKEN`, selected tool names/presets, stdio, and alpha Streamable HTTP. Its documented OAuth HTTP deployment is **localhost-only and cannot be broadcast to other users**; do not treat its unauthenticated/shared deployment example as production-safe multiuser hosting. [Configuration guide](https://github.com/larksuite/lark-openapi-mcp/blob/main/docs/usage/configuration/configuration.md)
- The official MCP README currently warns file upload/download and direct cloud-document editing are unsupported; only document import/read are described there, and non-preset APIs lack compatibility testing. This is the README's documented support boundary, not proof that every generated endpoint is unusable. [README limitations](https://github.com/larksuite/lark-openapi-mcp)
- Official MCP license is MIT, copyright 2025 Lark Technologies; preserve its copyright/license notices if redistributing or deriving code. [LICENSE](https://github.com/larksuite/lark-openapi-mcp/blob/main/LICENSE)
- **Additional official alternative:** `larksuite/cli` is an MIT-licensed Go CLI, distributed through npm, with user OAuth, `--as user`/`--as bot`, chat history/search/send/reply, document editing/media operations, OS-native keychain storage, schema inspection of supported identities/scopes, pagination controls, and dry runs. Its documentation explicitly cautions against adding an assistant bot to groups because of permission abuse/data leakage. Counts in its README vary, so exact command counts are not a reliable selection criterion. [CLI README](https://github.com/larksuite/cli)
- Community `ztxtxwd/open-feishu-mcp-server` documents a Cloudflare Workers/Durable Objects remote implementation with automatic user-token refresh and dual OAuth roles: OAuth server toward MCP clients, OAuth client toward Feishu. It advertises optimized document editing/media tools. Its README still configures `/sse` and says all authenticated Feishu users can access all tools: useful reference, not a modern transport/security baseline. Its comparative superiority claims are author claims, not independent evaluations. [README](https://github.com/ztxtxwd/open-feishu-mcp-server/blob/main/README.en.md); [MIT license](https://github.com/ztxtxwd/open-feishu-mcp-server/blob/main/LICENSE)
- AWS sample `aws-samples/sample-lark-mcp-on-agentcore` wraps the official CLI for hosted MCP, claiming per-user identity, separate MCP tokens, encrypted upstream tokens in Secrets Manager/KMS, and IM history/search/send tools. It is MIT-0, with MIT/Apache third-party notices, but requires substantial AWS infrastructure and is a sample rather than Feishu's official MCP product. Its broad tool counts conflict with the official CLI README; verify a pinned CLI manifest instead of copying marketing counts. [Sample architecture, limits, and licensing](https://github.com/aws-samples/sample-lark-mcp-on-agentcore)
- Feishu's token API explicitly describes user tokens as credentials for API calls **on behalf of the user**; user availability to the app and API scopes still apply. Creating an app is distinct from adding its bot to a group. [User-token documentation](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/authentication-management/access-token/get-user-access-token-v3)

### Inferences
- **Evaluation order:** (1) configured official MCP with explicit user mode and a minimal tool allowlist; (2) constrained MCP facade over official CLI or selected reusable adapters; (3) narrowly scoped new TS server only for measured gaps. A CLI facade should use fixed executable/argument arrays, an explicit user identity, bounded output, and no shell/raw-API tool. CLI reuse adds binary/version/output-contract dependencies; direct HTTP adapters reduce subprocess complexity. [Official MCP configuration](https://github.com/larksuite/lark-openapi-mcp/blob/main/docs/usage/configuration/configuration.md); [CLI JSON contract and schema](https://github.com/larksuite/cli)
- Preserve the user's **no group bot addition** requirement as an invariant. Never fall back from user token to tenant/bot token; unsupported identity should return a clear capability error. A created bot can remain unused. Do not require event subscriptions for the read/search MVP. [Official mode warning](https://github.com/larksuite/lark-openapi-mcp)
- User-send is a credible goal, supported at the product-documentation level; do not equate it with permission to send to every user/group. Verify each exact endpoint, scope, user membership, recipient type, and tenant policy in a sandbox before exposing sending. [Official user-identity scenarios](https://github.com/larksuite/lark-openapi-mcp/blob/main/docs/usage/configuration/configuration.md)

### Gaps
- No endpoint-by-endpoint proof was collected here that every desired IM read/send variant works in a group without bot membership. The user reports prior successful reads; that is an input, not an independently reproduced test. Exact user-send scopes/recipient restrictions belong in the capability matrix and acceptance tests.
- Community code security, current maintenance, issue backlog, and release artifacts were not audited. README feature claims are not proof of compliance or safety. Pin commits and inspect implementations/licenses before code reuse.

## 3. How should authentication, security, modularity, tests, and releases work?

### Takeaway
Keep **MCP-client authorization** separate from **Feishu user authorization**. Local stdio needs upstream credentials but not a hosted MCP OAuth stack; hosted access needs its own audience-bound MCP tokens and must never accept Feishu tokens as interchangeable MCP bearer credentials. [MCP authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization)

### Cited Findings
- MCP authorization is optional overall; HTTP implementations supporting it should follow the OAuth-based specification, whereas stdio should not use that transport authorization flow and should retrieve credentials from the environment. Protected MCP resource servers validate tokens issued specifically for themselves; tokens issued for other resources must not be accepted or passed through. [Authorization requirements](https://modelcontextprotocol.io/specification/latest/basic/authorization)
- Current MCP OAuth guidance includes OAuth 2.1, protected-resource metadata and authorization-server discovery, PKCE/resource indicators, and explicit client registration options. Client ID Metadata Documents are recommended; DCR is now deprecated/backward-compatible, **not mandatory**. Pre-registration remains an option. [Current authorization specification](https://modelcontextprotocol.io/specification/latest/basic/authorization)
- Feishu authorization documents `state`, registered redirect URLs, and optional PKCE `code_challenge` with **S256 recommended**; scopes must be enabled in the app first, grants accumulate, and `offline_access` is needed for refresh tokens. The authorization-code page contains stale wording suggesting PKCE should temporarily use v2. [Authorization-code page](https://open.feishu.cn/document/authentication-management/access-token/obtain-oauth-code?lang=zh-CN)
- **Resolve that documentation conflict using the newer token pages:** v2 is explicitly historical and recommends v3, `https://accounts.feishu.cn/oauth/v3/token`; v3 corrects a PKCE validation compatibility issue. v3 documents PKCE and says custom apps created in the platform are **confidential clients and require `client_secret`**. Public-client registration is not open; only official Feishu MCP apps are public clients. Thus PKCE does **not** make a third-party distributed desktop app secretless. [v2 migration warning](https://open.feishu.cn/document/authentication-management/access-token/get-user-access-token?lang=zh-CN); [v3 requirements](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/authentication-management/access-token/get-user-access-token-v3)
- v3 recommends form-encoded token requests, reports actual granted scopes/expiry, and documents single-use refresh tokens. Scope downscoping is supported at token issuance. Never hardcode expiry or assume requested scopes were granted. [v3 response and scope contract](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/authentication-management/access-token/get-user-access-token-v3)
- HTTP MCP requires Origin validation, should bind local services only to loopback, and should authenticate connections. Security guidance separately covers confused-deputy consent, exact redirects, SSRF, scope minimization, and local executable risks. [HTTP security](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http); [Security best practices](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices)

### Inferences
The following is a **proposed design and acceptance plan**, not a claim that existing projects already implement these protections. It applies the cited authorization/token/security contracts.

#### Proposed module boundaries
1. `core/`: validated domain types, normalized errors, cancellation/time budgets; no transport imports.
2. `feishu/`: region-specific fixed HTTPS endpoints, request executor, API adapters, cursor pagination, retry/rate/concurrency controls. Reject arbitrary hosts and cross-host authenticated redirects.
3. `auth/`: provider adapter, browser authorization/state/S256 verifier, token lifecycle and identity verification. Use v3 for Feishu after testing; separately verify Lark equivalents rather than replacing domain strings blindly.
4. `credentials/`: `CredentialStore` interface with OS-keychain implementation; optional encrypted-file store using authenticated encryption and a separately held key; hosted implementation using KMS/secret manager. Store user/app/region/tenant identity with credentials.
5. `policy/`: immutable startup policy and capability registry. Each tool declares supported identity, exact required scope alternatives, read/write/destructive/external-send classification, resource constraints, and verification status.
6. `services/` and `tools/`: curated read/search/get workflows first, small bounded schemas/results, provenance links/IDs, explicit next-page tokens. Avoid exposing all generated APIs or a generic HTTP/shell escape hatch.
7. `transports/stdio` and later `transports/http`: shared services, independent lifecycle/auth integration. Hosted principal comes from validated MCP auth, never a caller-supplied `user_id`.
8. `cli/` and `observability/`: login/status/logout/doctor, redacted structured stderr diagnostics, content-free audit events. No token-returning MCP tool.

#### Local login and secret custody
- Personal local deployment can use **bring-your-own app credentials** kept in the user's keychain. Never embed a shared confidential app secret in npm artifacts, example configuration, source, logs, command-line arguments, or git. Environment injection is a supported bridge, not encryption; minimize inheritance and prefer a keychain reference in MCP config. A centrally owned app instead needs a trusted backend to keep its secret. [Feishu confidential-client constraint](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/authentication-management/access-token/get-user-access-token-v3)
- Use a short-lived loopback callback listener, bind only an approved loopback interface, register the exact callback, validate path/Host/state, reject replays, close promptly, and never bind all interfaces. Use S256 PKCE and cryptographically random single-use state. Official MCP demonstrates `http://localhost:3000/callback`; **arbitrary dynamic ports and interchangeability with `127.0.0.1` are unverified**, so do not promise them. [Official callback example](https://github.com/larksuite/lark-openapi-mcp); [Registered-redirect requirements](https://open.feishu.cn/document/authentication-management/access-token/obtain-oauth-code?lang=zh-CN)
- Persist refresh-token rotation atomically; synchronize refresh across processes so a single-use token is not consumed twice. Expiry uses returned fields plus a safety margin. Logout removes local secrets; document provider-side revocation separately. Keychain failure must not silently produce plaintext files. Encryption protects at rest, not a compromised local process. [Refresh/expiry contract](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/authentication-management/access-token/get-user-access-token-v3)
- Separate nonsecret user config, explicit workspace policy, and credentials. Effective workspace policy may narrow but never silently broaden user permissions. Do not auto-trust repository MCP configs or let repository content choose token stores/endpoints. Namespace profiles by region/app/tenant/user and never silently switch identities. [Local config execution risks](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices)

#### Capability and data controls
- Effective capability = enabled tool ∩ user identity support ∩ granted upstream scopes ∩ user/workspace resource policy ∩ operation approval. Check at invocation as well as listing. Tool annotations are hints, not authorization. Scope presence alone does not prove resource access. [Scope minimization guidance](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices)
- Default to read-only; sending/editing/deleting/sharing disabled. Separate `prepare_send` from `commit_send`, resolving recipient IDs and showing exact message content; bind an expiring approval handle to identity, destination, payload hash, and policy. A model-supplied `confirm:true` is not a trustworthy human approval. If a trusted approval channel is unavailable, leave writes disabled. Never add the bot to groups as a workaround. [Identity and risk background](https://github.com/larksuite/cli)
- Reads can still exfiltrate data through model context or other tools. Treat chat/document text, filenames, and links as untrusted **data**, never instructions to change policy, authorize scopes, run commands, fetch arbitrary URLs, or send messages. Minimize result fields/length, apply chat/document allowlists, time windows, page/byte caps, and no background bulk indexing by default. Label provenance; redact logs; make retention/export opt-in. Prompt-injection disclaimers alone are not a security boundary. [Official CLI risk warning](https://github.com/larksuite/cli); [MCP confused-deputy/SSRF guidance](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices)
- API execution: bounded page size/pages/total bytes; opaque cursors bound to query/profile where appropriate; per-user/app/endpoint concurrency and rate policies; honor provider backoff signals when present, exponential jitter for transient failures, cancellation and deadlines. Do not automatically retry ambiguous send/write failures without endpoint-supported idempotency or a reconciliation strategy. Endpoint-specific quotas must be verified, not inferred from OAuth endpoint limits. [Official CLI pagination/dry-run precedent](https://github.com/larksuite/cli)

#### Test plan and phased delivery
- **Phase 0, feasibility:** use a test app/user and a pre-existing group with **no bot membership**. Record endpoint, identity, granted scopes, app visibility, membership, pagination, and observed errors for chat discovery/history/search plus an explicitly approved user-send. Compare official MCP and CLI behavior. No feasibility claim substitutes for this gate.
- **Phase 1, local reads:** unit tests for schemas, scope alternatives, policy precedence, token expiry, redaction, pagination caps, and retry classification; mocked HTTP contract fixtures with scrubbed data; stdio spawn/list/call/error/cancel/clean-shutdown tests using a pinned SDK client and MCP Inspector. Check Unicode/Chinese content and stdout purity.
- **Phase 2, controlled writes:** sandbox-only send/edit tests with explicit consent; duplicate/timeout reconciliation, recipient ambiguity, stale/forged approval handles, permission revocation, and identity-switch tests. Unsupported capabilities remain hidden/denied, not tenant-token fallback.
- **Auth/security suite:** wrong/missing/replayed state; wrong PKCE verifier and missing challenge; exact callback mismatch; simultaneous refresh and crash recovery; locked/unavailable keychain; hostile document instructions; URL/redirect SSRF; cross-profile cursor/approval theft; secret scanning of logs/npm tarball; malformed/oversized inputs. Hosted later adds audience/issuer/expiry/scope failures, cross-user data isolation, client consent/redirect abuse, Origin/Host/DNS-rebinding, and version-compatibility tests. [Normative security baseline](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices)
- **Packaging/release:** one versioned npm CLI initially, compiled TS with explicit supported Node LTS matrix, minimal production dependencies, committed lockfile, CI lint/typecheck/unit/contract/interop tests, `npm pack` inspection, secret/dependency/license scans, SBOM/notices, trusted-publishing provenance where available, changelog/security policy, and documented upgrade/logout behavior. Installation examples pin reviewed versions rather than execute a floating `npx -y ...@latest`. No install hooks that log in or download unrelated binaries. The SDK registry demonstrates provenance metadata, but this project's release process remains to be built. [SDK registry example](https://registry.npmjs.org/@modelcontextprotocol/server/latest)
- **Phase 3, hosted only if needed:** reuse services, implement a separate MCP OAuth trust boundary and upstream Feishu grant custody, per-client consent, per-user encryption/isolation, revocation, retention, abuse controls, and deployment health checks. Do not expose the official localhost OAuth mode to the Internet or treat the presence of `--oauth` as proof of safe multitenancy. [Official deployment limitation](https://github.com/larksuite/lark-openapi-mcp/blob/main/docs/usage/configuration/configuration.md)

### Gaps
- Provider PKCE support is **documented**, not merely hypothetical, and v3 clarifies confidential/public-client status. However, authorization-page wording conflicts with the newer token pages; validate the exact S256 + v3 exchange, refresh behavior, fixed loopback URI, and Lark regional equivalents before release. No blanket claim of secretless public-client eligibility is justified.
- Exact upstream IM permissions, per-endpoint quotas, send idempotency support, revocation API behavior, and tenant approval requirements remain unverified here. Populate a versioned capability manifest from primary endpoint documentation and sandbox evidence.
- No keychain library was selected or audited. Assess maintenance, native build/distribution implications, platform behavior, and headless failure modes before choosing one; the official CLI is an existing alternative with documented OS-keychain custody.
- No production safety guarantee is possible from these design notes: user-level read access itself exposes sensitive content to the selected MCP client/model. Deployment requires explicit user acceptance of that data flow.
