# Feishu user-token messaging feasibility and permissions

Research date: 2026-11-04. Planning/documentation research only: no credentials, console access, tenant inspection, OAuth login, or live API tests. Sources were retrieved during this session; publication dates shown by search engines are not evidence that a tenant supports a feature. User constraint: creating an app with bot capability is acceptable; never add that bot to target group chats. Read-only remains valuable.

## 1. Can an app read the user's conversations without adding its bot, and which exact routes apply?

### Takeaway

There is an explicit documented **user_access_token** path for message search, chat history, and individual message content; do not confuse it with bot-token access. The required read scopes and ordinary user visibility restrictions still apply. Group discovery is explicitly based on the **user or bot represented by the token**, not necessarily bot membership. [History](https://open.feishu.cn/document/server-docs/im-v1/message/list), [message get](https://open.feishu.cn/document/server-docs/im-v1/message/get), [search](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/message/search), [groups](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/chat/list).

### Cited Findings

All API paths below are relative to `https://open.feishu.cn/open-apis`. Scope punctuation is significant.

| Capability | Endpoint | User-token scope requirements and evidence |
|---|---|---|
| List joined groups | `GET /im/v1/chats` | `user_access_token` or tenant token; any one of `im:chat`, `im:chat:readonly`, `im:chat:read`, `im:chat.group_info:readonly`. Prefer current least-privilege `im:chat:read`. Lists groups of the token's user/bot; **does not include p2p chats**. Bot capability must be enabled on the app. [Official reference](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/chat/list) |
| Read group members | `GET /im/v1/chats/:chat_id/members` | User or tenant token; any one of `im:chat`, `im:chat:readonly`, `im:chat.members:read`, legacy `im:chat.group_info:readonly`. Operator **user or bot** must belong to group. Internal-group operator must be in same tenant. Bot members are excluded from returned members. [Official reference](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/chat-members/get) |
| History / thread replies | `GET /im/v1/messages?container_id_type=chat&container_id=oc_…` (or `container_id_type=thread`) | User token explicitly supported. Base scope **one of** `im:message` / `im:message:readonly`, **plus** `im:message.p2p_msg:get_as_user` for p2p, or `im:message.group_msg:get_as_user` for groups. Not merely the top-level OR scope table. [Official reference](https://open.feishu.cn/document/server-docs/im-v1/message/list) |
| Get full message content | `GET /im/v1/messages/:message_id` | User token explicitly supported; same base + chat-type-specific user scopes as history. Returns message body, sender, mentions, chat/thread IDs; merged-forward messages can return root and submessages. [Official reference](https://open.feishu.cn/document/server-docs/im-v1/message/get) |
| Preferred message search | `POST /im/v1/messages/search` | **User token only**, `search:message`. Searches messages visible to the user with the same visibility as in-app search; optional query and filters; result snippets plus metadata including chat/message/thread IDs. Not equivalent to full message bodies. 100 calls/minute; page default 15/max 30. [Official reference](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/message/search) |
| Older message search | `POST /search/v2/message` | **User token only**, `search:message`; returns message IDs, not full bodies; supports keyword, sender, chat IDs, p2p/group and time filters. Docs recommend switching to new IM search. [Official reference](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/search-v2/message/create) |

- History pagination is default 20/max 50; `start_time`/`end_time` use seconds. A normal group's chat-container history returns thread root messages, so use thread-container reads for the replies; thread reads do not support time ranges. [History](https://open.feishu.cn/document/server-docs/im-v1/message/list).
- For **application-token** history, the base can be `im:message`, `im:message:readonly`, or historical `im:message.history:readonly`; group reads additionally need `im:message.group_msg`. This is different from user permissions `im:message.group_msg:get_as_user` and `im:message.p2p_msg:get_as_user`. Do not substitute event/bot scopes `im:message.group_at_msg:readonly` / `im:message.p2p_msg:readonly` for user history permissions. [History's explicit identity-specific permission notes](https://open.feishu.cn/document/server-docs/im-v1/message/list); [official plugin's separate tenant/user permission lists](https://www.feishu.cn/content/article/7613711414611463386).
- `im:message.history:readonly` is marked an older-version permission in history documentation. Search-indexed official scope-list text additionally says it is no longer maintained and cannot newly be requested; the fetched scope-list body was only a dynamic placeholder, so the no-new-requests statement has weaker, snippet-only verification. New implementations should use the explicit current user-scope combination above. [History](https://open.feishu.cn/document/server-docs/im-v1/message/list); [scope catalog](https://open.feishu.cn/document/ukTMukTMukTM/uYTM5UjL2ETO14iNxkTN/scope-list?lang=zh-CN).
- Current history/get pages still contain generic prerequisites saying the **bot** must be in the group, even while their detailed permission notes and Authorization headers explicitly support user identity. This is an internal documentation ambiguity, not grounds to reject the user path. Feishu's permission guide states user-token data access matches the user's readable/writable scope, and its official 2026 plugin guide advertises user-identity p2p/group history and search with the exact supplemental scopes above. [History](https://open.feishu.cn/document/server-docs/im-v1/message/list); [get](https://open.feishu.cn/document/server-docs/im-v1/message/get); [permission guide](https://open.feishu.cn/document/ukTMukTMukTM/uQjN3QjL0YzN04CN2cDN); [official plugin](https://www.feishu.cn/content/article/7613711414611463386).
- User access is not unlimited history access: error `230073` describes thread invisibility when new members cannot view older history; `231203` describes restricted/secret chat types prohibiting copying; `231204` says apps with **external sharing or associated organizations enabled** do not support history requests as user. Individual message get can return `230050` (message invisible) and `230110` (deleted). [History errors](https://open.feishu.cn/document/server-docs/im-v1/message/list); [get errors](https://open.feishu.cn/document/server-docs/im-v1/message/get).
- Returning/using employee-style `user_id` adds `contact:user.employee_id:readonly`; `open_id` avoids that extra field permission but is app-specific. [Member list](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/chat-members/get); [message search](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/message/search).

### Inferences

- Recommended read-only scope set: user-type `im:chat:read`, `im:message:readonly`, `im:message.group_msg:get_as_user`, `im:message.p2p_msg:get_as_user`, `search:message`; optionally `im:chat.members:read` and `offline_access`. This is a synthesis of documented per-route requirements, not a verified tenant manifest. [History](https://open.feishu.cn/document/server-docs/im-v1/message/list); [groups](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/chat/list); [search](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/message/search); [OAuth](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/authentication-management/access-token/get-user-access-token-v3).
- Search can be a useful smaller-scope first milestone: `search:message` alone is documented for snippets/metadata. Full-body hydration/history is a separate capability requiring read scopes. New search metadata includes `chat_id`, including p2p results, which helps discovery because group-list excludes p2p. Do not promise an exhaustive recent-DM list or archive from search. [Search](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/message/search); [groups](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/chat/list).

### Gaps

- No live no-bot-in-group history/get test was performed. The generic bot-prerequisite wording conflicts with explicit user support; record this discrepancy and validate on an ordinary joined group after credentials exist, **without adding the bot**.
- No complete DM-list API was verified. Search supplies relevant p2p IDs, not guaranteed exhaustive enumeration.
- No paid-plan requirement specific to these read endpoints was found in their references. This is not proof that all free tenants, retention policies, external chats, encrypted chats, or older messages are supported.
- Exact review exemption/sensitivity status of each requested user read scope must be checked in the target app console; general docs do not enumerate the exception list.

## 2. Can the app send, reply, edit, recall, react, and handle files as the user?

### Takeaway

**Send and reply as the user are explicitly documented**, requiring the exact pair `im:message` + **`im:message.send_as_user`**. They are tenant-dependent, not categorically impossible: Feishu's own guide warns some enterprises (including ByteDance) do not support user-identity sending. Editing and attachment endpoints have narrower documented token support and must not be assumed to work with user tokens. [Send](https://open.feishu.cn/document/server-docs/im-v1/message/create), [reply](https://open.feishu.cn/document/server-docs/im-v1/message/reply), [official tenant restriction](https://www.feishu.cn/content/article/7613711414611463386).

### Cited Findings

| Operation | Endpoint | Documented tokens / scopes / constraints |
|---|---|---|
| Send as self | `POST /im/v1/messages?receive_id_type=chat_id` | User token supported; **both** `im:message` and `im:message.send_as_user`. Dot before `send_as_user`, not a colon. Bot send scopes alone do not authorize sending as a user. `receive_id` supplies chat ID; text body uses serialized JSON. [Send](https://open.feishu.cn/document/server-docs/im-v1/message/create) |
| Reply as self | `POST /im/v1/messages/:message_id/reply` | User token supported; same pair `im:message` + `im:message.send_as_user`; optional `reply_in_thread`; optional `uuid` deduplicates within one hour. [Reply](https://open.feishu.cn/document/server-docs/im-v1/message/reply) |
| Edit message | `PUT /im/v1/messages/:message_id` | **Only tenant_access_token is documented**. OR scopes `im:message`, `im:message:send_as_bot`, `im:message:update`. Text/post only, current operator's own message only, max 20 edits, administrator-defined edit window. No documented user-token edit path established here. [Edit](https://open.feishu.cn/document/server-docs/im-v1/message/update) |
| Recall, not local delete | `DELETE /im/v1/messages/:message_id` | Tenant **or user token**. OR scopes `im:message`, `im:message:recall`, `im:message:send_as_bot`; identity-specific availability of each scope must be respected. Docs describe bot own-message recall and group owner/admin recall; tenant-defined time limits. User-token support does not grant blanket recall of others' messages. [Recall](https://open.feishu.cn/document/server-docs/im-v1/message/delete) |
| Add reaction | `POST /im/v1/messages/:message_id/reactions` | Tenant or **user token**; OR scopes `im:message` / `im:message.reactions:write_only`. Explicit prerequisite: **bot or user** must be in conversation. Returns operator type/user ID and reaction ID. Recalled/system messages cannot be reacted to. [Reaction](https://open.feishu.cn/document/server-docs/im-v1/message-reaction/create) |
| Upload message file | `POST /im/v1/files` | **Tenant token only** in reference; `im:resource` or `im:resource:upload`. Bot capability required, nonempty file ≤30 MB, returns file_key. This is not Drive's file_token. [Upload](https://open.feishu.cn/document/server-docs/im-v1/file/create); [send content notes](https://open.feishu.cn/document/server-docs/im-v1/message/create) |
| Download message resource | `GET /im/v1/messages/:message_id/resources/:file_key?type=image\|file` | **Tenant token only** in fetched reference; OR scopes `im:message`, `im:message:readonly`, historical `im:message.history:readonly`. Explicit bot-in-session condition and error `234004` app not in chat. ≤100 MB; restrictions on stickers, merged-forward submessages/cards, restricted messages. Do not claim this documented route meets no-bot group download constraint. [Resource download](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/message-resource/get) |

- Send/reply docs retain bot-in-group prerequisites despite explicit user-token sections, just like history docs. The user-send path is real and officially advertised, but those pages alone do not cleanly state the no-bot exception in prerequisite prose. This should be a targeted validation point, not dismissed as impossible or silently guaranteed. [Send](https://open.feishu.cn/document/server-docs/im-v1/message/create); [reply](https://open.feishu.cn/document/server-docs/im-v1/message/reply); [official plugin guide](https://www.feishu.cn/content/article/7613711414611463386).
- The official plugin guide explicitly says: “以用户身份发消息需在飞书开放平台额外开通机器人 im:message.send_as_user 权限，部分企业（如字节）不支持此操作。” It separately advertises user-identity message sending, replying, reading, searching, and image/file download. Thus lack of this scope in a tenant is an actual product restriction, while attachment support advertised by the plugin does not resolve the tenant-only token contract in the fetched resource endpoint reference. [Official guide](https://www.feishu.cn/content/article/7613711414611463386); [resource endpoint](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/message-resource/get).
- Scope-list search results classify `im:message.send_as_user` as “高级” (advanced); the underlying dynamic catalog could not be fully retrieved. Stronger fully fetched evidence is the endpoint's explicit scope pair and the official guide's tenant restriction. Do not infer universal allowlisting, historical grandfathering, or a guaranteed approval process from the “advanced” label alone. [Catalog](https://open.feishu.cn/document/ukTMukTMukTM/uYTM5UjL2ETO14iNxkTN/scope-list?lang=zh-CN); [send](https://open.feishu.cn/document/server-docs/im-v1/message/create); [official guide](https://www.feishu.cn/content/article/7613711414611463386).
- Send/reply errors include tenant communication controls (`230035`), DLP/content review (`230028`), cross-tenant p2p denial (`230038`), unsupported encrypted messages (`230075`), and group speaking restrictions (`230018`). These references combine bot/user cases, so do not assume every error has identical applicability to both identities. [Send](https://open.feishu.cn/document/server-docs/im-v1/message/create); [reply](https://open.feishu.cn/document/server-docs/im-v1/message/reply).

### Inferences

- Implement sending/reply as an **optional capability**, enabled only if both exact user scopes are available and granted. Do not silently fall back to bot sending or suggest adding the bot when the user's requested no-bot mode is active. This follows the identity-specific documented permission split. [Send](https://open.feishu.cn/document/server-docs/im-v1/message/create).
- Read-only should ship independently of sending. Reactions are a separate permission/capability; user-send restriction does not, by itself, establish a reaction prohibition. [History](https://open.feishu.cn/document/server-docs/im-v1/message/list); [reaction](https://open.feishu.cn/document/server-docs/im-v1/message-reaction/create).
- Do not expose user edit or arbitrary attachment downloads as guaranteed features. Uploading with tenant identity and sending a file key as user may be possible, but ownership interoperability must be verified; the send endpoint documents resource-owner errors. [Upload](https://open.feishu.cn/document/server-docs/im-v1/file/create); [send](https://open.feishu.cn/document/server-docs/im-v1/message/create).
- Require explicit confirmation for sends/recalls and show acting user and target. Feishu itself recommends preview-and-confirm for user-identity writes. [Official security guidance](https://www.feishu.cn/content/article/7613711414611463386).

### Gaps

- No definitive public rule was established for which tenants can newly obtain `im:message.send_as_user`, whether platform support can enable it, or whether any older apps have exceptions. Never promise that requesting support will succeed.
- No live no-bot-in-target-group send/reply test; no current target-tenant scope catalog. This is a conditional feature, not verified for this user.
- Reaction creation is verified; reaction list/removal endpoint details were not independently fetched in this pass. Creation docs link deletion and identify the returned reaction ID.
- User-token recall is explicit, but precise own-user-message eligibility and which scopes can be requested under user identity require console/API validation. No distinct “delete only from my view” route was established.
- Official plugin attachment claims conflict with narrower fetched public resource-reference token support; the precise official user-download route/scope or special entitlement remains unresolved. Do not use private endpoints/cookies to bridge this gap.

## 3. Does user consent remove app/admin approval, and what does this imply for an open-source TypeScript MCP?

### Takeaway

**No blanket no-administrator-approval promise is justified.** Feishu distinguishes per-app scope enablement, release/tenant approval rules, user consent/token grants, app availability, and the user's actual resource permissions. There are legitimate automatic-approval policies and developer user-token debugging exemptions, but the docs expressly exclude some sensitive user scopes from review-free debugging; exact messaging-scope eligibility is unresolved without the console. [Permission guide](https://open.feishu.cn/document/ukTMukTMukTM/uQjN3QjL0YzN04CN2cDN); [review policies](https://open.feishu.cn/document/best-practices/intro-to-custom-app-review).

### Cited Findings

- **Token identities:** tenant-token scopes authorize app identity; user-token scopes authorize the consenting user identity. User-token resource access follows the user's own readable/writable data scope and needs no separate app data-range configuration. Per-app scopes still have to be applied for; another app's grants do not transfer. [Permission guide](https://open.feishu.cn/document/ukTMukTMukTM/uQjN3QjL0YzN04CN2cDN).
- **App credentials are not a user login:** current OAuth exchange requires an authorization code and app identity; codes last five minutes and are single-use. The user must have app availability. Current Feishu token endpoint is `POST https://accounts.feishu.cn/oauth/v3/token`; the old `open.feishu.cn/open-apis/authen/v2/oauth/token` is deprecated. [v3 reference](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/authentication-management/access-token/get-user-access-token-v3); [v2 migration warning](https://open.feishu.cn/document/authentication-management/access-token/get-user-access-token).
- **Important MCP architecture restriction:** apps created in Feishu Open Platform are **confidential clients** and must supply `client_secret`. Public-client registration is not open; only Feishu official MCP apps are public clients, and they must use PKCE. Do not design a new third-party open-source MCP assuming secretless public OAuth client enrollment is available. [v3 client_secret requirements](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/authentication-management/access-token/get-user-access-token-v3).
- **Consent is granular:** token exchange `scope` can only narrow authorized permissions, not add them; returned `scope` is authoritative because the server may trim requested scopes. `offline_access` is needed to obtain a refresh token; refresh tokens are single-use; expiry values should be read from response, not hardcoded. [OAuth v3](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/authentication-management/access-token/get-user-access-token-v3).
- **Normal custom-app release:** modifications to features, scopes, basic info, or subscriptions require a version release and enterprise approval. Admins can configure app-specific automatic approval or scope-based review-exemption policies; otherwise all apps require review. Thus “no manual approval this time” can mean an administrator previously authorized a policy, not absence of governance. [Custom app review](https://open.feishu.cn/document/best-practices/intro-to-custom-app-review).
- **Documented developer exception:** when a scope supports review-free developer user-token debugging, the app developer can test without publishing or waiting for review. The same guide says some sensitive user-token permissions **cannot** be debugged without review. It does not identify all such scopes. A separate test-company mechanism has automatically approved test scopes, but those grants do not take effect in the formal app/production tenant. [Apply-for-permissions guide, testing and release sections](https://open.feishu.cn/document/ukTMukTMukTM/uQjN3QjL0YzN04CN2cDN).
- **Store apps:** official permission guide describes platform app-listing review and tenant installation/update review; advanced permissions need a significant reason. Making the repository open source is not itself a platform scope grant or tenant installation approval. [Permission guide](https://open.feishu.cn/document/ukTMukTMukTM/uQjN3QjL0YzN04CN2cDN).
- **Restricted scope availability is real:** batch-import scope validation can explicitly reject a scope because it does not exist **or the app is not eligible to apply**. A copied permission JSON is therefore not evidence of granted permissions. [Batch import section](https://open.feishu.cn/document/ukTMukTMukTM/uQjN3QjL0YzN04CN2cDN).
- **Feishu China vs Lark:** the concrete API and OAuth evidence above is for `open.feishu.cn` / `accounts.feishu.cn`. Feishu's official plugin guide says its plugin also supports Lark; the old search reference itself links to a Lark-hosted replacement document. This establishes shared capability documentation, **not** identical tenant scope availability or interchangeable credentials. [Official plugin](https://www.feishu.cn/content/article/7613711414611463386); [old search reference](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/search-v2/message/create).

### Inferences

- Feasibility verdict: **proceed with read-only user-token architecture; make user sending optional; treat strict no-admin setup as conditional, not universally satisfied or universally impossible.** Personal developer debugging may offer a documented low-friction path if each required scope permits it; released production apps depend on existing tenant review policy. [Developer exemption and review rules](https://open.feishu.cn/document/ukTMukTMukTM/uQjN3QjL0YzN04CN2cDN).
- Suggested open-source distribution: bring-your-own custom app credentials configured locally, separate Feishu/Lark realm configuration, explicit user OAuth, protected secret/token storage, serialized refresh rotation, capability checks from actual granted scopes, and no implicit tenant-token fallback. BYO confidential credentials avoids embedding a shared secret in published TypeScript. This is an architectural recommendation grounded in v3 confidential-client requirements, not a platform-prescribed deployment model. [OAuth v3](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/authentication-management/access-token/get-user-access-token-v3).
- Suggested validation order once user authorizes setup: (1) inspect app eligibility for the minimal **user-type** scopes and review status; (2) confirm bot capability and user app availability without joining groups; (3) obtain OAuth token and inspect returned scopes; (4) list user groups; (5) search; (6) history/get for an existing joined group with absent bot and then a p2p chat; (7) only if sending scope is available, explicitly confirmed self-send/reply; (8) attachment investigation as an independently gated feature. These checks directly target the documented scope/token distinctions and unresolved prerequisite wording. [Groups](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/chat/list); [history](https://open.feishu.cn/document/server-docs/im-v1/message/list); [send](https://open.feishu.cn/document/server-docs/im-v1/message/create); [OAuth](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/authentication-management/access-token/get-user-access-token-v3).

### Gaps

- Target tenant, user role/developer membership, app creation policy, app availability, review exemptions, message retention, security controls, and plan are unknown. No claim of “works without admin approval for you” is possible yet.
- Exact public Lark OAuth v3 endpoints/client-registration rules and per-scope differences were not independently verified; do not mechanically replace hosts or reuse China credentials. Verify against Lark's own references before supporting that realm.
- No documented paid-plan gate specific to the core endpoints was established, but neither was universal free-plan availability. Rate limits cited are endpoint references, not verified tenant quota entitlements.
- No special/restricted-app entitlement should be assumed for a newly created third-party MCP just because Feishu's official MCP/plugin has a capability. Public-client eligibility is explicitly official-MCP-only in the retrieved v3 reference.
- No browsing of private APIs, cookie reuse, scraping, or security-control bypass is proposed. Unavailable scopes should produce a clear unsupported/approval-required result while preserving independently available read-only functionality.
