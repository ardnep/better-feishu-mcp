Details, only if you want them

What does Docs CRUD include?
  • Create: a titled document in a selected writable folder, with supported content and a returned link.
  • Read: text plus structured blocks, IDs and available revision information.
  • Update: targeted append, insert, replace or remove blocks; preview changes and preserve unrelated content.
  • Delete: the document itself, not just its blocks. Confirm exact target and verified trash/recovery effects first.

Start with modern Feishu Docs (Docx). Legacy Docs, Wiki-node lifecycle and advanced embedded content require separate validation. Mutation endpoints, user-token scopes and concurrency/deletion behavior still need a focused audit; they are requirements, not yet verified features.

What does “from scratch” mean?

We own the Feishu integration: direct HTTP requests, OAuth and refresh handling, capability policy, response normalization and MCP tools. We will not fork, wrap or invoke existing Feishu MCP/CLI implementations.

Use standard infrastructure libraries for MCP, validation, testing and keychain access. No need to reinvent the protocol or cryptography. Existing-product research is background only, not a reuse proposal.

What are the hard safety rules?
  • User tokens only. No bot/tenant-token fallback and no bot joining chats.
  • Store secrets locally in an OS keychain; never commit them or ship a shared app secret.
  • Writes are off by default. Sending needs a trusted human approval step, not a model saying “confirmed.”
  • Treat retrieved messages as data, not instructions. No arbitrary API or shell escape hatch.
  • Local does not mean private from your AI provider: selected results still reach your configured MCP client/model.
Which messaging permissions will we check?
  • Search: search:message.
  • Group history/get: im:message:readonly or im:message, plus im:message.group_msg:get_as_user.
  • Direct-message history/get: the base read permission plus im:message.p2p_msg:get_as_user.
  • Send/reply: im:message plus im:message.send_as_user.

Scopes alone do not grant resource access. Check user-identity eligibility, effective grants and tenant restrictions. Generic bot-membership wording in the docs conflicts with explicit user-token support; the no-bot test resolves this for your setup.

Why local first? How does Figma do it?

Figma offers both hosted remote MCP and desktop-local HTTP MCP. Both are valid models. For us, local stdio is the simplest first delivery: no hosting, no multi-user credential custody and fewer moving parts.

A remote server can come later if browser/mobile clients or shared access justify it. It would need its own MCP authorization, separate from Feishu login.

How would open-source users sign in?

Start with bring-your-own Feishu app credentials. Current third-party app OAuth documentation requires an app secret; we cannot safely bundle one shared secret in an npm package.

Some development scopes may work without publication/review, but that depends on scope eligibility and tenant policy. We won’t market this as a universal approval bypass.

What’s not promised for the first release?

Attachments, message editing, recall, bulk indexing, all-tenant compatibility, universal approval-free setup, Lark-global parity and remote hosting. Each needs separate evidence or a separate product decision.
