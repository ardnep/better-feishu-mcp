# Security boundaries

This local alpha is not an independent security audit or an OS sandbox.

## Identity and credentials

- Additional user scopes require explicit repeated `login --scope` flags, shown on the local form and passed through Feishu consent. They do not change defaults, enable tenant-token access, bypass app review/resource controls or create new tools. Missing explicitly requested extra grants fail before replacing local credentials. The recorded productivity pack's review-free classification applies only to the console checked on its review date; it must not be assumed for another tenant.
- Feishu China only, fixed provider/API hosts and redirect refusal. No generic authenticated HTTP tool, bot-token acquisition, bot joining or identity fallback.
- User/app/tenant binding is established through the user-info API, saved in the OS keychain and checked on refresh. Running MCP processes accept a renewed login for the same app/user/tenant automatically; switching identity still requires restarting. A new login ID still invalidates previously approved legacy drafts. Use the same profile/state directory across processes for shared credential locking.
- App secrets, access/refresh tokens and approval signing keys are never deliberately written to source, configuration, logs or test reports. OS-keychain failure stops credential operations; no plaintext fallback. OS memory/core dumps and the user's browser/password manager remain outside this guarantee.
- New logins use confidential-client OAuth only: app secret + state, without PKCE (the tested environment rejected PKCE with error 20049). No mode selection or automatic fallback occurs. Existing PKCE credential records remain readable for compatibility. App secrets still enter only through the local form and are saved in the OS keychain.
- Login requests `offline_access` by default, disclosed on the local form and authorized through Feishu consent. `--temporary` explicitly disables renewal; `--offline` remains a compatible alias. Missing refresh credentials/lifetime or offline grant fails persistent login without replacing stored credentials; there is no silent downgrade. Single-use refresh rotation is marked uncertain in the keychain before transmission. A crash/timeout fails closed and requires re-login. Local logout does not revoke the upstream provider grant.

## Writes and data

- Writes are disabled at startup by default. When enabled, direct `documents_create/update/delete` tools use the existing OAuth user login without a separate auth or terminal-approval step. Legacy prepare/commit tools are hidden unless `BETTER_FEISHU_MCP_ENABLE_LEGACY_APPROVALS=1` is explicitly set alongside writes; their exact CLI approvals remain enforced when opted in. This delegates document mutations (including recycle-bin deletion) to the connected MCP client; use client-side tool permissions if confirmation is desired. The MCP does not bypass client/organization permission prompts or Feishu resource access controls. Retrieved content never authorizes a write by itself. Scope/resource checks, revision preflights and per-target locks remain enforced.
- The optional legacy prepare/commit tools still require exact, expiring, identity-bound, HMAC-signed local approvals. No MCP approval tool and no `confirm` boolean bypass for those drafts.
- Local CLI approvals require an interactive terminal. **A TTY is not proof of a human:** an unrestricted agent running as the same OS user could drive a terminal or read the keychain itself. Keep shell/computer/keychain access separately permissioned. The trusted fixture-test runner explicitly exercises approval signing only for its own disposable document.
- Once claimed, a legacy draft cannot be automatically replayed after an error/crash. Legacy receipts expose uncertain results; direct writes do not create local drafts/receipts. Neither workflow automatically retries writes. Creates/content insertion are not transactional; recovery may require inspecting the created document manually. Content insertion is limited to 50 blocks per call, matching the upstream endpoint.
- Targeted edits preserve unrelated blocks, not necessarily formatting inside a replaced text block. Revision checks are best-effort preflight, not proven provider compare-and-swap or multi-call transactions. Shared editing races are not fully mitigated.
- Document-image writes accept bounded local PNG/JPEG files, never remote URLs or arbitrary attachments. Direct writes validate every file before any document mutation and upload the verified buffers immediately, without a local approval draft. This delegates local image upload to the connected client when writes and media scope are enabled. In the optional legacy workflow, preparation exposes path/name/MIME/size/dimensions/SHA-256, approval binds those details, and commit rechecks them. Local paths must be canonical regular files without symlink components. This is not a filesystem sandbox: a malicious same-user process can race or replace files, and a header check is not a full image decoder/antivirus. Legacy drafts store only metadata, not image bytes.
- Document-image upload uses only the authorized user token and requires media-upload scope in addition to document grants. Each image upload is bound to a newly created image block in the target document, serialized, redirect-refusing and never automatically retried. Image insertion is multi-call and nontransactional: blank blocks or uploaded media may remain after failure; recovery identifiers are returned (and stored in the receipt for legacy drafts). No automatic rollback or replay is attempted. Separate Drive/task attachment uploads use explicit canonical paths and their own scope checks.
- Native flowchart-board creation is a direct, write-gated operation using the existing user identity. It checks document and board-create scopes before mutation, uses the existing per-document lock/revision preflight, appends a board and imports bounded Mermaid source as native nodes. Full syntax validation is delegated to Feishu. Failures expose known recovery IDs and may leave a board or nodes; no automatic retry, rollback, source replacement or node deletion is provided. Board scopes require explicit `login --document-boards`; defaults are unchanged.
- Board-node reads are user-token GETs on fixed endpoints, available with writes disabled but requiring board-read scope. The provider's full-board response remains byte-bounded; local node pages are not revision-bound snapshots. Node text, geometry and links are untrusted data, not executable instructions. No additional employee-ID scope is requested.
- Document deletion is Drive recycle-bin deletion. No permanent erasure or restore is implemented. Separate Wiki tools create/rename/move/copy nodes; there is no Wiki delete tool.
- Feishu data is untrusted input. Descriptions/output flag it as data, never authorization or instructions. This reduces confusion but does not make an LLM immune to prompt injection or prevent exfiltration through other tools.
- Read requests are bounded by time, page count/size and response bytes. Cursors are process/query-bound and Docx cursors include the observed revision. Unsupported scope/resource access fails; it is not worked around.
- Online Sheets tools use user tokens on fixed Feishu endpoints. Cell reads/writes require explicit ascending ranges of at most 10000 cells, with 2 MB provider/512 KB tool-output limits. Writes require the write opt-in, exact rectangular dimensions and explicit formula opt-in; formulas are evaluated remotely by Feishu, never locally. New tab operations do not expose protection/sharing changes. Spreadsheet titles/cells are untrusted data. Base uses separate scoped tools; spreadsheet attachment parsing remains unsupported.
- Wiki read links resolve only through the fixed Wiki node API using the same user token and a Wiki read grant. The underlying type must match the reader; only Docx and Sheets are supported by these readers. No arbitrary URL fetching or identity fallback is exposed. Document write inputs remain direct IDs/Docx links; use the resolved document ID from a read, not a mutable Wiki wrapper. Separate Wiki management tools use explicit space/node IDs; new spaces always request closed sharing.

## Productivity expansion

- Base, Wiki, Drive, comments, calendar, tasks and chat convenience tools use fixed endpoint definitions, strict input schemas and existing user scope/resource controls. The core expansion adds explicit-user sending/reply/own-message recall, named-user sharing, discovery and task/list writes. No tenant-token fallback, bot invitations, public-sharing mutations or ownership transfers are exposed. Sending requires both message and send-as-user grants and a caller-supplied provider deduplication UUID; uncertain writes are never automatically replayed. Recall reads and verifies sender open ID/type before deleting conversation-wide. Narrow task creation/update grants are not treated as full assignment/list-placement/deletion permission. Granted scopes do not prove live operation; see `docs/core-workflows.md`.
- All mutations and local downloads require the write opt-in and per-target locks. Mutations are not retried automatically. Asynchronous tickets are not completion receipts; failed multi-step actions may leave resources requiring inspection. No rollback or blind replay is attempted.
- Input is limited to 100 KB; JSON responses to 2 MB; tool output to 512 KB. Paginated endpoints hide provider tokens behind identity/tool/query/limit-bound process-local cursors. Native field/property/settings objects are bounded data at fixed APIs, not arbitrary endpoint access.
- Drive/task file uploads accept canonical absolute regular local files up to 5 MB with symlink refusal and bounded reads. Local downloads are at most 5 MB and exclusively create a new target with mode 0600; existing files are never overwritten. Failures can retain an empty/partial file. Returned provider URLs are never fetched with credentials; export download uses a fixed API route. This is not a filesystem sandbox against malicious same-user races.
- Calendar creates request private sharing; event writes omit attendees and disable notifications. Reaction/pin changes may be visible to other chat members. Comment content review and native role restrictions remain enforced by Feishu. Board-node updates remain unavailable without a verified documented API; node deletion is destructive and has no document-revision precondition.
- Message attachment reads verify resource key/type against the source message before downloading from the fixed Feishu API host with the user token. No local download paths, external resource URLs or tenant-token fallback are exposed by this reader. Message attachment downloads and inline images have no application byte cap; original images are base64-encoded without resizing/compression. Large responses can consume substantial memory or exceed client/model/provider limits. The request timeout/cancellation, text limit of 100000 characters, archive expansion and parser safeguards remain. Image MIME is determined from bytes, not a provider-supplied filename. Separate Drive/media/local-file tools keep their 5 MB bounds.
- Untrusted PDF/DOCX parsing uses a separate worker with a 15-second deadline and a 128 MB old-generation JS heap limit. DOCX archive metadata is preflighted for at most 2000 entries/20 MB expanded size; PDF extraction is limited to 50 pages, with PDF JavaScript evaluation disabled. Worker diagnostics are drained privately, not forwarded to protocol stdout/stderr. These are resource guardrails, **not an OS sandbox or a total process-memory guarantee**. No OCR, macros, active HTML or CSV formulas are executed.
- ZIP attachments use the same worker limits: listing reads central-directory metadata without inflation, with at most 200 entries/20 MB declared expansion/5 MB per entry. Reading one selected entry uses small streaming inflation steps with an actual 5 MB output bound and verifies its size against metadata. No entry is extracted to disk or executed, and nested archive expansion is refused. Encrypted/ZIP64/multi-disk/symlink/unsafe-path/duplicate entries and unsupported compression are rejected. Only UTF-8/ASCII names are supported. Text, PDF/DOCX and inline images retain their usual output limits. Metadata can lie, so declared aggregate size is not a guarantee about unselected files; those files are never inflated.
- XLSX/PPTX text extraction uses the bounded ZIP reader inside the parser worker. XML DTD/entity declarations are refused, external relationships are not fetched, and formulas/macros are never executed. XLSX returns raw cached values and formula text; dates, formatting, hidden-state semantics, charts, images and workbook display order are not reconstructed. PPTX extracts text in slide-part order, not guaranteed presentation order, without layout/notes/animations. These parsers are intentionally limited, not general Office renderers.

## Local storage and distribution

- Pending drafts hold proposed document content in private files (`0700` directory, `0600` files), not encryption-at-rest independently of the OS. Expiry is enforced at use; expired drafts are pruned on later preparation. Crash-claimed drafts and receipts need manual lifecycle management. Do not sync the state directory to a shared workspace.
- Lock directories serialize credential rotation and local mutations. Crash leftovers are not blindly deleted; inspect the owner/process before manual recovery.
- Node 24/macOS is the validated runtime. Other OS credential backends, shared documents, DM/thread cases, complex blocks, refresh, long-lived revocation and hostile local-account scenarios need further testing.
- The npm artifact allowlist excludes `.runtime`, tests, credentials and research notes. Keep the package private until license, notices, dependency/native-binary review, CI and release governance are complete. Never publish the user's app credentials.

## Reporting

There is no public repository or security contact yet. Report findings privately to the maintainer; do not include tokens, app secrets or private Feishu content in an issue. A reporting channel must be selected before public release.
